# 02 — Non-Negotiable Requirements

Keep all of these in scope; do not dilute.

## Voice — real full-duplex
Local always-listening "Jarvis" wake word, push-to-talk, and keyboard activation; streaming STT and streaming TTS; natural turn-taking; barge-in (I can interrupt while it speaks); VAD, echo cancellation, noise suppression; optional local speaker verification; whisper/quiet modes; configurable length/formality/urgency; spoken approvals, warnings, and summaries; measured latency, false-wake, interruption, and accuracy metrics; offline fallback. Use a distinct, restrained British-style synthetic voice — do NOT clone or imitate Paul Bettany or any specific actor. Every engine (wake word, STT, TTS, VAD, noise suppression, speaker verification, audio routing) must be a replaceable open-source component.

## Model gateway — provider-neutral
Separate routable roles (fast conversation, deep reasoning, coding, vision, STT, TTS, embeddings, reranking, planning, verification, safety review, tool selection, agent routing, long-context, local fallback). Support Anthropic-native, OpenAI-compatible, Gemini-compatible, Ollama, and configurable local/remote endpoints, with capability/context/tool-use/multimodal discovery, structured-output validation, cost/latency tracking, privacy classification, automatic fallback, manual pinning, and per-agent/per-tool policies. Core logic must not couple to any one provider's message format.

Use a LOCAL-CAPABLE-FIRST routing policy: prefer local models when they meet the task's quality, latency, tool-use, and context requirements; use cloud models only for an explicitly configured capability or quality lift. 128 GB makes many large quantized local models (including some 70B-class) practical, but whether a local model fits depends on quantization, context length, KV-cache, concurrent agents, vision/speech services, and DB/app memory — so do NOT mandate that every task use a large local model. The whole system must run fully offline (local Ollama-compatible models, local STT, local TTS, local embeddings) when configured, and I must be able to disconnect external providers and complete a workflow.

## Computer control — full macOS computer-use
Screen capture, Accessibility APIs, semantic UI-tree inspection, window/app discovery, mouse, keyboard, clipboard, app launching/switching, file operations, browser automation, terminal, AppleScript/JXA, Shortcuts, via native macOS plugins / Tauri / Rust / Swift bridges. Prefer semantic APIs, accessibility trees, CLIs, app APIs, and DOM access over coordinate-based clicking (coordinates only when nothing structured exists). Every action must be observable, interruptible, logged, permission-scoped, verifiable, and reversible where possible. Before any consequential action, show what will happen, which apps/files/accounts are affected, the proposed commands/UI actions, the reason, the risk, whether it's reversible, the rollback plan, and the required approval.

## Dynamic capability platform & self-extension
Do NOT depend on a permanently predetermined connector list. Build registries for agents, tools, skills, rules, prompts, workflows, models, devices, hardware plugins, MCP servers/clients, integrations, simulators, displays, and sensors. Use MCP as the primary external tool/context protocol, plus adapters for local CLIs, HTTP/OpenAPI/GraphQL, WebSockets/webhooks, databases, filesystems, and (later) Home Assistant, MQTT, Matter, Thread, Zigbee, Z-Wave, Bluetooth, serial/USB, ROS 2, and hardware. J.A.R.V.I.S. must be able to discover MCP servers/tools, inspect OpenAPI/CLI help, and generate typed integrations, new tools, skills, rules, agents, workflows, hardware/display/sensor plugins, simulators, tests, docs, schemas, and permission manifests — and diagnose, repair, version, and roll back its own capabilities.

Self-extension is the HIGHEST-RISK subsystem and is split into two stages with a mandatory gate between them:

- **STAGE A — GENERATION WITHOUT ACTIVATION:** detect the missing capability; search existing registries before creating anything; research authoritative docs; verify licenses; define a typed contract, permission manifest, and risk classification; define test requirements; generate the implementation in an isolated Git worktree/sandbox; generate unit + integration + security + failure tests; run formatting, type-checking, tests, static analysis, dependency + secret + license scans; run against fixtures and in a restricted sandbox; produce a human-readable capability report, code diff, permission summary, and risk summary. It may NOT install or activate anything in Stage A.
- **DEDICATED CHECK-IN:** a design-and-security review checkpoint with me, specifically for the self-extension engine itself and again for any high-risk generated capability, before any activation path is enabled.
- **STAGE B — CONTROLLED ACTIVATION (only after that check-in):** request explicit approval; install a signed/hashed artifact; activate with minimum permissions; observe initial executions; verify the first real result; store provenance/version/audit; automatically disable or roll back on defined failures. Hot-reload only where proven safe, and never on activation-by-passing-tests alone.
- **HARD LIMIT:** no generated capability may ever create, alter, or bypass security policy, approval policy, audit logging, emergency-stop controls, credential storage, sandbox enforcement, permission-escalation logic, or the capability-installer security itself.

## Autonomy & approval
Default policy: read-only inspection/retrieval may run automatically; low-risk reversible local actions may run automatically when explicitly delegated; external communication, account changes, purchases, financial actions, security changes, privacy-sensitive operations, destructive/irreversible actions, and consequential physical-device actions all REQUIRE approval; high-risk physical control requires explicit per-action approval plus hardware interlocks. Every tool call carries a risk classification. Support allow-once / allow-for-task / allow-for-session / always-allow-in-scope / deny / revoke / pause / cancel / emergency-stop, with a persistent emergency-stop control in every major interface. PROHIBITED, non-negotiable: autonomous weapons, unauthorized system access, bypassing access controls, covert surveillance, credential theft, malware, hidden persistence, disabling safety mechanisms, undisclosed impersonation of me, and unauthorized purchases/communication/physical-control.

## Memory — local, encrypted, user-controlled
Distinct stores (conversation, episodic, semantic, procedural, preferences, people, relationships, projects, decisions, documents, entities + relationships, routines, locations, device state, hardware, skills/learned procedures, long-running objectives, corrections/feedback, task history, spatial anchors, room/display configs, capability history, model performance, hardware compatibility). Use PostgreSQL + pgvector (or a verified open-source local equivalent); no proprietary hosted vector DBs. Every item carries provenance, confidence, created/updated/last-used dates, expiration, retention rules, and sensitivity labels, with encryption at rest and field-level protection where appropriate. Provide search, view, correction, pinning, forgetting, export, deletion, full reset, backup, restore (with verification), and duplicate/conflict detection. Memory MUST distinguish verified facts vs user statements vs external claims vs inferred preferences vs temporary context vs simulated data vs uncertain vs superseded vs deleted. Never store secrets in conversational memory — use the OS keychain or a local encrypted secrets vault.

## Proactive behavior — movie-style but controlled
Morning/evening briefings, meeting prep, calendar-conflict detection, surfacing important communications, commitment/deadline tracking, continuing approved long-running tasks, monitoring selected topics, detecting device/service/network anomalies, next-action suggestions, and bringing relevant info forward before I ask. Gate it with quiet hours, priority levels, confidence thresholds, duplicate suppression, escalation policies, per-domain permissions, rate limits, snooze/dismiss, and an explanation of why each alert appeared. Proactive messages must be relevant and sparse — no continuous commentary. Never act consequentially without approval.

## Cinematic functional interface
Recreate the FUNCTIONAL visual language of Tony Stark's interfaces WITHOUT copying movie frames, Marvel artwork/logos, proprietary sound effects, soundtrack, actor likenesses, or production assets. Use layered transparent surfaces on dark backgrounds, fine technical typography, cyan/blue operational states, amber advisory, red critical, white focal info, radial/orbital diagnostics, fine grids, wireframes, depth/parallax, motion that communicates state, proper lighting/shadows, smooth camera movement, readable silhouettes, and progressive disclosure — plus reduced-motion, high-contrast, and scalable-type accessibility. Every animation must communicate state, causality, priority, relationship, progress, warning, completion, or failure. Do NOT build a generic neon dashboard, meaningless circular charts, fake code, random telemetry, static movie skins, or unreadable noise — everything on screen must have a function. Build all interface modes as real vertical slices (live data or a clearly-labeled simulator, never an empty screen), in phases: Command Center, Ambient Voice Orb, Iron-Man-style HUD (weapons/targeting replaced with safe equivalents — object selection, inspection, navigation, search regions, robotics/drone test targets, rescue planning, structural/environmental analysis, diagnostics), Workshop (engineering copilot), Holotable, Mission Control, Home Control, Communications, Intelligence, and Health/System Telemetry (authorized data only; no medical diagnosis; never present inferred health as fact).

## Five-state capability classification
Maintain a living MCU capability-parity matrix classifying EVERY capability as exactly one of: REAL (working functionality) / HARDWARE-DEPENDENT (production adapter, simulator until hardware exists) / SIMULATED (clearly-marked SIMULATION adapter with the same typed contract) / DEFERRED / PROHIBITED (with documented reasoning). No capability may disappear from the matrix without explanation. Simulation modules must display a permanent SIMULATION state and never be confused with live telemetry.
