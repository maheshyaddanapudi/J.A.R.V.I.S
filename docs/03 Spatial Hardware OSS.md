# 03 — Spatial / XR / Hardware, and Open-Source & Platform Constraints

## Spatial / XR / hardware (architecture now, implementation phased)
Quest 3S, Quest 3, Apple Vision Pro, OpenXR, and WebXR are FIRST-CLASS architectural targets even though their implementation comes in later phases. Use OpenXR as the primary cross-platform XR abstraction where supported; Apple Vision Pro must NOT be the sole spatial target. Build a hardware-neutral shared Spatial Scene Service so the SAME J.A.R.V.I.S. object is renderable through browser, desktop, projector, transparent display, light-field display, volumetric display, Vision Pro, Quest 3S/3, OpenXR, WebXR, and a flat-screen 3D fallback — maintaining room geometry, display/sensor/user positions, hand/head/gaze data where supported, anchors, object coordinates, occlusion, capabilities, and cross-device synchronization. Query device capabilities at runtime and degrade gracefully (never assume eye tracking, depth, body tracking, passthrough quality, or hand-tracking precision are present).

For every spatial platform, verify the currently supported official input and privacy APIs during Phase 0 and again before implementation. On Apple Vision Pro, do NOT design the core interaction model around access to raw gaze coordinates; use official privacy-preserving system interactions such as look-and-pinch, hover, focus, and supported gestures/visionOS abstractions. Raw gaze data may be used only if a current official API explicitly permits the required use case and the associated privacy, entitlement, and distribution constraints are documented and approved.

Projection-mapped rooms, light-field displays, and volumetric displays are FUTURE HARDWARE ADAPTERS: design the abstraction and typed contracts now, maintain researched adapter stubs and tested simulators, and implement each only when hardware is selected/available. Classify display plugins honestly (surface projection / transparent planar / stereoscopic / light-field / volumetric / head-mounted MR / experimental empty-air) and NEVER claim conventional projectors, transparent screens, light-field panels, or headsets produce true empty-air holography.

## Hardware catalog & plugins
Build a living, researched hardware catalog and plugin marketplace so hardware can be added without modifying the core. For each candidate product, record manufacturer, exact model, category, status, price, availability, official page, retailer links, local-API/SDK availability, supported OSes, open-source-driver availability, license, Home Assistant / ROS / OpenXR / WebXR support, required adapters, privacy/network/internet dependency, integration effort, recommended use, alternatives, LAST VERIFICATION DATE, and known limitations. Never claim a product is available or compatible without current verification, and never purchase anything automatically. Named products (e.g., webcam/MediaPipe hand tracking, Ultraleap Leap Motion Controller 2, Looking Glass light-field displays) belong in the researched catalog — they must not define the architecture.

## Open-source & platform constraints
All server-side services, core application frameworks, data stores, orchestration, and replaceable runtime dependencies MUST be open source. Proprietary OS APIs, hardware SDKs, firmware, and drivers may be used ONLY when required for explicitly selected hardware/OSes (macOS, iOS, watchOS, visionOS, Meta Horizon OS, Quest, Vision Pro, cameras, spatial/volumetric displays, projectors, smart-home, robotics, sensors) — and only when isolated behind replaceable adapters, documented in a license/proprietary-adapter registry, given an open alternative where one exists, never a hard dependency of the core orchestration/memory/agent/tool platform, and failing gracefully when the hardware is absent. Do NOT introduce proprietary hosted infrastructure, databases, observability, vector stores, queues, or workflow systems. Flag any GPL/AGPL/non-commercial dependency and prefer permissive (MIT/Apache-2.0) alternatives; if you must use a copyleft/NC component, surface it at a check-in first.
