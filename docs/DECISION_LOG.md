## D-0075 — Fast-model memory judgments (entity resolution, fact merge, topic extraction) + self-authored & reusable skills
- **Date:** 2026-07-20 · **Status:** APPROVED by the user ("if we need a separate LLM call, let Jarvis look at the records and decide to merge or not rather than some code fuzzy logic — do it with the fast model, unless it's not better"). Also: "let Jarvis write skills MD" and "the skill or code written by Jarvis should be accessible and reusable."
- **Context:** the 70/30 observation run (OBSERVATION_RUN_2026-07-19) left four open bugs — (2) name-variant entity duplicates ('Pepper' vs 'Pepper Potts'), (4) noisy learned-topic extraction (grabbed 'quick'/'one-line'/'intuition'), (5) a concurrency race in `rememberEntity`, and (3) no self-creation path for no-code skills. The user directed that merge/resolution decisions use a **fast-model judgment** rather than brittle string heuristics where the model is genuinely better.
- **Decision — where a judgment beats a heuristic, use the fast model; keep the heuristic as a strict fallback:** a new `MemoryJudge` (`src/memory/judge.ts`, backed by the gateway's `fast_conversation` role) makes three calls the string logic did poorly: (a) **entity resolution** — is a similarly-named mention the SAME real-world thing? a positive match accrues the mention to the canonical entity + records the variant as an ALIAS (migration 0025 `aliases text[]`), so recall by either name resolves to one entity; (b) **fact-merge consolidation** — which of an entity's facts RESTATE each other (replaces the jaccard/stem loop during the quiet-hours pass); (c) **deep-topic extraction** — the specific subject a correction is about (replaces the filler-grabbing `salientTerms`).
- **Non-negotiable contract (honesty + local-first):** every judge method is BEST-EFFORT and returns `null` on ANY failure (offline / no eligible provider / timeout / parse error / gate off), and the caller then runs the existing DETERMINISTIC path — the judge never blocks or throws into a memory write. Privacy-respecting: the call carries a privacy class derived from row sensitivity (private/secret → LOCAL_ONLY, which the gateway keeps on-device; a remote-only fast model then simply yields the fallback). Off-switch: the `memory.llmJudgment` setting (default on, D-0058 catalog). It only ever proposes MERGES/RESOLUTIONS — every merge supersedes-with-history (walkable, reversible); nothing is hard-deleted on a model's say-so. This lives OUTSIDE Z1 and never touches `assessDepth` (which stays deterministic + zero-latency by design).
- **Bug 5 (concurrency):** `rememberEntity` now takes a transaction-scoped `pg_advisory_xact_lock` on the canonical (name, kind) and re-resolves the supersede set under the lock, so parallel same-name inserts serialize to one active row.
- **CROSS-KIND RESOLUTION 2026-07-20:** the observation run's real duplication source was same-name across DIFFERENT KINDS (the model tags 'arc reactor' as `thing` one session, `project` the next) — which the per-(name,kind) unique index and the same-kind judge candidate set both left untouched. Closed via the fast model, both directions: (1) **prevention on write** — `fuzzyCandidates` now surfaces similar/exact-named active entities of ANY kind (exact-name matches first); when there's no same-kind exact match, the judge sees cross-kind candidates and a positive match accretes the mention into the existing entity (its kind kept), so no cross-kind duplicate is created. (2) **healing in consolidation** — a new `mergeEntities` judge decision + `EntityMemory.mergeEntityInto` fold pre-existing same-name-different-kind actives into one during the quiet-hours pass (facts/relations/aliases migrated forward, supersede-with-history, live-collision-safe), surfaced in the sleep-cycle report. Both are best-effort and NEVER automatic — the judge decides, so genuinely different same-name things stay distinct. `resolveEntity` now returns the matched candidate INDEX (unambiguous when candidates share a name across kinds) instead of a name. 383 kernel tests (+4: cross-kind prevent/keep-distinct/heal + judge `mergeEntities`). Live real-brain (Haiku): 'arc reactor' thing+project → merged to one; 'Mercury' planet+element → kept distinct; a seeded 'Repulsor' thing/project duplicate → healed by consolidation with both facts preserved; every judgment in `/gateway/calls`.
- **REFINEMENT 2026-07-20 (prefer fuller name + advisory-lock residual):** (1) canonical-name selection now **prefers the FULLER name** — when a variant resolves to an existing entity, the more complete name wins ('Pepper' arriving after 'Pepper Potts', OR 'Pepper Potts' arriving after 'Pepper', both settle on 'Pepper Potts') and the shorter form is demoted to an alias; this also fixed a latent bug where re-mentioning by an alias could rename the entity to the short variant. (2) On the advisory-lock residual: investigation showed the **structural backstop already exists** — migration 0010 created a partial UNIQUE index `(lower(name), kind) WHERE active`, so same-(name,kind) active duplicates are already impossible at the DB level. The residual was therefore not missing structure but concurrent writes hitting unique-VIOLATION failures; the advisory lock resolves that by serializing them into clean supersede+inserts (no lost writes). A proposed redundant index migration was dropped. The only genuinely-open case is cross-variant simultaneous creation (two brand-new spellings at the same instant → different locks), which is **self-healing** (next-mention resolution + quiet-hours consolidation merge them) and does not occur at single-user sequential scale; a per-kind lock spanning the judge call would guarantee it but trades concurrency for a case that doesn't arise. 379 kernel tests (+3: fuller-name promotion both orders, alias-no-rename, the structural-backstop guard).
- **Skills — self-authored + reusable (asks 1 & 2):** J.A.R.V.I.S. previously could not author or re-run a no-code skill (HTTP-only). New gated tools (`src/skills/tools.ts`): `skill.save` (LOW_REVERSIBLE — authors a reusable named objective, `createdBy: jarvis`), `skill.list` (READ_ONLY — discover), `skill.run` (CONSEQUENTIAL — reuse via the gated agent; recursion-guarded against nested skill.run; privacy-first LOCAL_ONLY default, opt-in STANDARD). Code capabilities were already reusable (`capability:<name>` tools + `selfext.listActive`, D-0073/74); this closes the no-code half so BOTH a skill and self-written code are discoverable and re-runnable.
- **Why this is "better" (the user's caveat):** across stateless sessions the model names the same real thing inconsistently and restates facts in ways a bag-of-words can't reconcile — a semantic judgment is the right tool; the heuristic remains as the offline-correct floor. Where the heuristic already suffices (exact-name re-mention), no model call is made (a cheap pre-filter gates every call, so cost tracks only ambiguous cases).
- **Verified 2026-07-20:** 376 kernel tests (19 new: entities resolution/merge/lock, judge parse/validate/fallback, reasoning extraction, skill tools). Live real-brain (Haiku fast / Sonnet-5 deep): 'Pepper' resolved to canonical 'Pepper Potts' (one active entity + `pepper` alias, recall by both, survived restart); consolidation merged two restatements below the 0.7 heuristic (`memory-fact-consolidation → claude-haiku-4-5 ok`); two filler-heavy corrections produced learned topic `['palladium']` (no filler); `skill.save`→`skill.list`→`skill.run` authored, discovered, and ran a skill end-to-end (real `system.info` → synthesized report), audited as `jarvis`. Every judgment appears in `/gateway/calls` served by the fast model. Key env-only, scrubbed (0 hits). Record: `docs/verification/D0075_MEMORY_JUDGMENT_2026-07-20.md`.

## D-0074 — Code-authored capabilities run in-container; "novel code needs a Mac" was WRONG (corrected)
- **Date:** 2026-07-19 · **Status:** APPROVED (correction of an inaccurate claim, verified in this environment).
- **What was wrong:** earlier verification docs said J.A.R.V.I.S. needs the Mac for "novel-code" self-extension. That conflated "a hardened isolation sandbox" (a future enhancement) with "the ability to write and run new code" (which already exists here). J.A.R.V.I.S. has a REAL gated `bash -lc` terminal (`src/terminal/`, DENY-first command policy, workspace-scoped) and REAL gated file-writing (`workspace.writeNote`, `files.edit`). So it can write a genuinely new program to its workspace and execute it — in THIS container, no Mac.
- **What is now enabled (this session):** a self-written PROGRAM becomes a **reusable capability** by composing `terminal.run` over it in a `selfext.draft` — safe by construction (the code runs as an external subprocess through the gated terminal, never loaded into the Z1 trust-core process). The one blocker was that a capability's composed steps waited on their own approval; fixed by **propagating the caller's approval decision to the fixed, reviewed composed steps** (`ToolContext.autoApprove`, populated per-call by `CoreLoop.runTool`, read by the `capability:<name>` executor). This NEVER widens what's allowed — policy still evaluates each step DENY-first. Live-verified: J.A.R.V.I.S. wrote a twin-prime sieve, ran it, and turned it into `capability:twin-prime-finder` that computed `primes<=100: 25; twin-prime pairs: [(3,5),(5,7),…]`; a `wiper` capability composing `rm -rf /` was REFUSED at the terminal policy. 356 kernel tests (incl. the approval-propagation test).
- **What the Mac genuinely adds (interface/hardening, not core):** a heavier isolation sandbox (dedicated worktree/container) + dep/SBOM/license scanning for a hardened generation pipeline at scale, and running fully-untrusted generated code. The CORE — write code, run it, reuse it — needs no Mac.
- **The one boundary that IS deliberate (safety, not hardware):** self-written code is never loaded as a NATIVE in-process kernel tool (that could reach Z1). It runs as an external subprocess via the gated terminal. R-CAP-08 unchanged.

## D-0027 — MCP client host built; raising a server's trust above `untrusted` is a check-in (T2)
- **Date:** 2026-07-17 · **Status:** PROPOSED — **granting an MCP server trust above `untrusted` is a per-server check-in decision (docs/06).**
- **Decision:** The dynamic-capability platform's **MCP client host** (`kernel/src/mcp/`) is built and **live-verified against a real stdio MCP server** (official SDK 1.29, spec 2025-11-25). It connects + handshakes, discovers the server's real tools, and registers each as a namespaced kernel tool (`mcp:<server>:<tool>`) wired through the full policy/approval/audit/verification pipeline. THREAT_MODEL **T2** is enforced structurally:
  - Everything a server returns is **UNTRUSTED content** — tool names/descriptions/schemas are labeled untrusted, never merged into system instructions, never treated as commands.
  - Tools are **namespaced** so a malicious server cannot shadow a built-in tool name (verified).

  - **Persisted (migration 0007, `mcp_servers`):** trust + manifest fingerprint + quarantine survive a kernel restart. A rug pull that occurs *while the kernel is down* is therefore still caught on the next reconnect, and a trusted server does not silently drop back to untrusted (which would re-prompt). The DB is the source of truth for these security-relevant fields.

## D-0057 — Brain-graph vector recall made scale-efficient: pgvector HNSW ANN index
- **Date:** 2026-07-18 · **Status:** IMPLEMENTED (migration 0016; found during the deep memory/efficiency pen-test)
